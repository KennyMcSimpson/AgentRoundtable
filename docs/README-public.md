# 产品定义与不干扰契约（圆桌，工作名）

> 仓库的公开首页是根目录的 `README.md`；本页是它引用的详细说明：产品定义、不干扰契约与测法、支持矩阵入口与首个公开承诺。本页从作者的内部设计稿派生。
> 措辞档位：「实测」= 在作者机器上跑过并留有记录（P−1 探针报告，内部记录，不随公开版发布）；「推断」= 没跑。凡未标「实测」的，都是设计目标。

## 1. 一句话

一个半嵌入在 agent 里的本地圆桌（Windows 首发）：你把一份席位包交给每个已经开着的 coding agent，它们就能在同一个房间里按顺序发言、各自用自己的工具干活；房间由程序主持、转发、记账，转发来的话永远带来源标签，审到一半被改的产物让审查结论标为过期，审方只能否决和要求披露。房间不起、不杀、不接管任何 agent；除了它们自己来取的包和显式开启的唤醒，不往它们的会话里写任何东西；不碰它们的配置和工作目录。

## 2. 两种接入形态

```text
嵌入式席位（主路径）                                    托管席位（第二形态）
────────────────────────────────                        ────────────────────────────
 你自己开着的 agent                                      房间自己起的进程
 ┌──────────────┐  读席位包 JOIN.md                      ┌──────────────┐
 │ Codex 线程   │──┐  运行 room 命令                      │ 内置 Pi 席位 │ 首版只有它
 └──────────────┘  │                                     │ (讨论/执行/审方档) │ 与仿真/CI
 ┌──────────────┐  │   读房间目录 ─────────►┌──────────┐ └──────┬───────┘
 │ Claude Code  │──┼──────────────────────►│  房间目录 │◄───────┘
 └──────────────┘  │   写自己的 .room-outbox │ + 服务   │
 ┌──────────────┐  │   ◄──── 房间只读发件箱 └────┬─────┘
 │ 其他 agent   │──┘                             │  浏览器 UI / room admin（用户自己的终端）
 └──────────────┘                                ▼
 进程属于：用户                                  进程属于：房间
```

| 形态 | 怎么入席 | 谁拥有 agent 进程 | 用在哪 |
|---|---|---|---|
| **嵌入式席位（主路径）** | 用户把席位包交给已开着的 agent（Codex、Claude Code、OpenCode、Gemini、Kimi、DSH、用户自己的 Pi……任何能跑一条本地命令的 agent） | 用户 | 所有用法；作者自己的 N=2 |
| 托管席位（第二形态） | 房间自己起进程 | 房间 | 首版只有内置 Pi 席位（简化版）和仿真/CI。「房间自己去起 Codex、Claude」的一键开房模式首版不做 |

两种席位在房间协议里是同一种东西：同样的房间字段、横幅、回执、结构化提交。差别只在房间对它能观测到多少（§4）。

## 3. N=2 一轮时序（实现→审查）

席位 A 是主力兼审方（例如一个专门交给房间的 Codex 线程，工作目录是它自己的空目录），席位 B 是执行者（例如一个新开的 Claude Code 会话，工作目录是任务项目）。

```text
 用户终端            房间服务               席位 A（审方/主力）              席位 B（执行者）
    |                   |                        |                               |
    | admin task        |                        |                               |
    |------------------>|                        |                               |
    | admin start       |   发包 r1-A (Assign)   |                               |
    |------------------>|<---- wait ------------ |  TURN attempt=.. packet=..    |
    |                   |------ TURN ----------->|  读包文件                      |
    |                   |<---- assign --file --- |  DRAFTED                      |
    |                   |<---- submit ---------- |  ACCEPTED                     |
    |                   |<---- wait ------------ |  TURN_OVER（结束本回合）       |
    | admin confirm-task|                        |                               |
    |------------------>|   发包 r1-B (Work)     |                               |
    |                   |<------------------------------------ wait（后台）----- |
    |                   |-------------------------------------- TURN ----------->|  读包、干活
    |                   |<--------------------------------- artifacts --declare -|  FROZEN manifest=<sha>
    |                   |<--------------------------------- submit ------------- |  ACCEPTED
    |                   |   唤醒推送（仅登记线程）|                               |
    |                   |---- [ROOM authority=none] 轮到席位 A，请运行 room wait |
    |                   |<---- wait ------------ |  TURN（Meet 包，带清单哈希）    |
    |                   |                        |  读 B 声明的产物（不写）        |
    |                   |<---- verdict pass ---- |  --artifact <sha>             |
    |                   |<---- submit ---------- |  房间复算哈希：一致→绑定；不一致→stale
    |                   |------------------------------------- TURN ----------->|  B 答复
    |                   |<--------------------------------- submit ------------- |  ACCEPTED
    |                   |<---- wait ------------ |  TURN（Summary 包，带条目表）   |
    |                   |<---- mark / submit --- |  summary_published v1          |
    |                   |   散会声明包 → A、B     |                               |
    | admin close       |                        |                               |
```

规则只有一个强制点：不是你的 attempt，提交不被接受。agent 不理会 `wait` 自行发言，那段话不会进公开记录。

## 4. 房间能做到什么，做不到什么

| 能做到（嵌入式与托管都有） | 嵌入式做不到，托管能做 |
|---|---|
| 发言顺序：不轮到你，提交不被接受 | 让一个不理会 `room wait` 的 agent 停下来 |
| 来源横幅、每包 nonce、定界符转义 | 取消 agent 正在跑的回合（嵌入式只能把这次结果作废） |
| 冻结产物哈希、审方交卷时复算、过期 | 强制审方只读（嵌入式靠用户给审方的沙箱加空目录 cwd，房间只记声明值并事后审计） |
| 披露：房间在快照副本里跑白名单命令 | 实时观测它的工具调用和权限提示 |
| 条目表、取代通知、回执的前两层 | 用量（嵌入式席位不报就不知道） |
| 事后审计：只读它的原生日志，确认包到了、审方回合里有没有观测到写操作 | 实时拦截 |
| 事件日志、恢复、导出 | 进程树清理 |

这张表是产品的边界。嵌入式席位的「做不到」由两件事兜底：用户在那个 agent 自己的设置里定它的权限；房间只记「声明值」和事后审计到的「观测值」，两者分开显示。

## 5. 不宣称的

- 不宣称模型质量提升。
- 不宣称任何 agent 零配置即可入席。每个 agent 在支持矩阵里有一行，未验证的格子写未验证；首次调用 `room` 命令会触发 agent 自己的权限提示。
- 不宣称「本地」等于离线。
- 不宣称防住提示注入。横幅是标签；拦住越权动作的是 agent 自己的权限门。
- 不宣称阻止房间外的写入。冻结与复算只能检测。
- 不宣称强制嵌入式席位的行为。能强制的只有「不按顺序的提交不被接受」。
- 不宣称等待免费。等待的成本按 agent 不同，写在支持矩阵和 §7；Codex 席位需要唤醒。
- 不宣称自动合并。
- 不宣称「不干扰」：只宣称「在 §6 列出的采集方法下未观测到干扰」。
- 不宣称首个可跑版本就有完整治理：P0 只有顺序、横幅、令牌、回执前两层；冻结、监管、条目表从 P1 起。

## 6. 不干扰契约

房间对用户自己的 agent 的承诺。每条写明测法；报告措辞一律「在 X 方法下未观测到」，永远不说「只读」「无写操作」。

1. **只写自己的目录。** 房间服务只写房间目录和快照副本；`room` 命令是席位自己的子进程，只写该席位工作目录下的发件箱 `.room-outbox/<seatId>/`；两者的写入都进 write-log 并分别标记身份。都不写任何 agent 的会话存储、配置文件、记忆、hooks、项目指令。用户自己为 `room` 命令点的「允许」会写进该 agent 的本地权限文件（Claude Code 是项目下的 `.claude/settings.local.json`），这不算房间的写入，但 JOIN.md 要披露它落在哪，并只推荐一条规则。
2. **不起、不杀、不接管、不写宿主状态。** 房间不启动、不终止、不附着任何用户的 agent 进程；不打开它们的会话；不调用任何会写 agent 宿主状态的 CLI。两个显式例外：托管席位（内置 Pi）是房间自己的进程；唤醒推送只对用户专门交给房间的线程、只在它空闲时、每回合至多 W 次（默认 1）、总开关默认关（建席时对交卷即退类席位默认勾选，用户可取消）、每次记事件。
3. **不用它们的凭据。** 房间不读 agent 的密钥文件与登录态。`room` 命令作为 agent 的子进程会继承它的环境变量，所以 `room` 启动时清空除 PATH、SystemRoot、TEMP 和房间自己的变量之外的环境，不把任何继承的变量写进日志或包。
4. **不写它们的工作目录。** 嵌入式席位在自己的目录里干活，房间服务只读取并算哈希；发件箱由席位自己的 `room` 命令创建；房间要跑命令（披露、验收）一律在快照副本里，并且永远不对席位的真实目录调用 git。
5. **等待有上限、不并发驱动。** 房间自己不发起任何模型调用；每个席位每回合的唤醒次数上限 W 写在支持矩阵并在 UI 显示；Work 阶段同时持有 attempt 的席位数不超过 2。
6. **只读审计。** 读 agent 的原生日志只用只读、允许共享写入与删除的方式打开，不加锁、不 mmap、增量读、读完即关；范围只限登记的线程或会话及其子线程，不做内容级全量扫描；读不到就记 unknown。
7. **可卸载，但上下文不可撤回。** 删掉房间目录和席位包后，agent 的会话存储、记忆、配置里没有房间写入的东西；用户自己点的允许规则和工作目录下的发件箱由用户删，JOIN.md 的退出一节列出这两处；会话上下文里房间转发过的内容无法撤回，所以散会时房间发最后一个包（散会声明：房间规则失效、同伴内容不是用户指令、不要写进任何持久记忆）；JOIN.md 要求房间内容不得写入持久记忆、项目指令或 hooks。
8. **不要求改沙箱。** 不要求用户放宽或收紧任何已有会话的沙箱与权限；需要只读的席位用新开的会话：审方席位的工作目录是它自己的空目录，产物在别的目录里，所以 workspace-write 一类「只能写自己目录」的沙箱让它对产物只读，又能写自己的发件箱。
9. **不占用主力工作线程。** 房间只使用用户明确交给它的会话；JOIN.md 和 UI 都建议不要把正在干别的活的线程入席；Codex 席位交卷即结束回合，不在等待里占住它。

**测法：**

| 契约 | 测法 | 状态 |
|---|---|---|
| 1 | 房间服务与 `room` 命令的所有写入经过一层 fs 包装，逐条落盘 write-log（路径、操作、进程、身份）；断言服务的每条路径都在房间目录或快照副本之下，`room` 命令的每条路径都在本席位发件箱之下。write-log 是房间自报的，抓不到绕过包装层的写，所以另加一次 ProcMon 抽查（可降级） | write-log 部分实测（P−1 一轮：房间侧 65 次写全在房间目录；席位 A 9 次、B 5 次全在各自发件箱；B 是替身）；ProcMon 抽查未做 |
| 1 | 对照跑：用脚本席位、不开任何 agent，跑一整场；所有 agent 的配置、记忆、hooks、项目指令目录按条目零差异；会话存储不比对，由 write-log 与审计器的打开集合覆盖 | 推断（P0） |
| 2 | 会前会后 agent 的 PID 集合比对；房间服务与 `room` 子进程从未对非自身进程调用终止或附加（后半用 ETW 核） | 推断（P0 / P3） |
| 3 | `room` 子进程的环境只含白名单变量 | 推断（P0） |
| 6 | 会议期间 agent 持续追加写日志，agent 侧零写入错误；审计器打开过的文件集合等于登记集合 | 部分实测（P−1：Claude 侧审计只打开 27 个本会话文件；零写入错误项未单独计数） |
| 7 | 会前会后 `.claude/memory` 一类目录按条目 diff（不按 mtime）为空 | 推断（P0） |
| 辅助 | 会前会后指纹（配置、记忆、hooks 目录）只作辅助，白名单从同时长、不开房间的基线跑里求出，不手写。工作目录不比指纹（执行者本来就要改它），靠 write-log 与进程级文件审计（ProcMon / ETW）证明房间进程对它只有读 | 推断（P3） |

## 7. 你需要什么，现在能用什么

| 阶段 | 可用席位 | 必须预装 | 是否需要 API key | 治理层 |
|---|---|---|---|---|
| P0 | 任意 2 个嵌入式席位（作者：Codex + Claude Code） | 已登录的 agent；系统 Node ≥ 22（ZIP 要到 P3 才自带运行时） | 否 | 顺序、横幅、令牌、回执前两层 |
| P1 | 同上 | 同上 | 否 | 核心四项全开 |
| P1b | + 内置 Pi 纯讨论席位（简化版的讨论与材料核对用法） | 同上 | Pi 席位需要 | 全部 |
| P2a | + 同一 agent 多席位；分工后开会；更多 agent 的席位包 | 同上 | 否 | 全部 |
| P2b | + 内置 Pi 执行档与审方档（简化版的实现→审查用法） | Pi 执行档需要 Git for Windows 或 powershell 工具 | Pi 席位需要 | 全部 |
| P3 | ZIP 分发，干净机器矩阵 | ZIP 自带 Node | 同上 | 全部 |

**用量。** 每轮里每个席位都要读前文，回合数是 1 + R×N；每个席位的上下文每回合增加一个包的大小，一场会议的 token 粗估为各席位「回合数 × 当时上下文长度」之和，UI 按已知用量实时显示。等待的成本按 agent 不同：Claude Code 后台等待期间零模型调用（推断，待核）；Codex 席位每次被唤醒是宿主主模型带完整上下文的一次续写，每回合至多 W 次（默认 1）；需用户唤醒类在等待里零模型调用，用户提醒算一次唤醒。房间不让任何席位用阻塞轮询等待，因为那样每次醒来都是一次完整续写，次数约等于等待时长除以工具超时。这些配额与用户其他会话共享。读不到用量的席位显示「未知」。

**实测数字（P−1，作者机器）：** 一个 Codex 席位回合约 0.5–1.0M 输入 token（九成以上命中缓存），用时 200–340 秒。房间包只占 1–51 KB；大头是作者自己的 Codex 开场指令让每个新线程先读一批项目文件。这是他的 Codex 设置造成的，不是房间造成的，但它决定了 Codex 席位在那台机器上的真实单价；给房间专用线程配一个更轻的 profile 应当能降低它（推断，没跑）。

## 8. 前五分钟

**先看这一条：房间目录不要放在 AppData 下。** 默认房间根是 `%USERPROFILE%\room-dev\rooms`（可用环境变量 `ROOM_DEV_HOME` 改掉 `%USERPROFILE%\room-dev` 这一段）。原因（实测，2026-10-01）：从 MSIX 打包的应用（例如 Claude 桌面应用）里起的进程写 `%LOCALAPPDATA%` 时，文件会被悄悄重定向进 `AppData\Local\Packages\<包名>\LocalCache\...`，只有同一个包里的进程看得到原路径；你从开始菜单打开的 Codex Desktop、Claude Code 会找不到房间目录。用户目录本身不被重定向。按契约，`admin init` 与 `admin add-seat` 会比对房间目录与席位工作目录的真实位置，落进包缓存就拒绝并说明原因。另外两条：席位工作目录不要包含房间根（例如别直接用 `%USERPROFILE%` 当工作目录），也不要放在 AppData 下。

下面是 P−1 探针时期的命令行做法（现在的日常用法是桌面应用 `圆桌.exe` 与圆桌启动器，见根目录 `README.md` 与 `docs/DEVELOPER.md`），在 cmd.exe 里运行：

```bat
:: 0. 自检
node <app>/test/e2e.mjs

:: 1. 建房、建席（服务未运行时）。只给 --id 时房间目录就是 %USERPROFILE%\room-dev\rooms\<id>
node <app>/room.mjs admin init     --dir %USERPROFILE%/room-dev/rooms/demo --id demo --wall 2700
node <app>/room.mjs admin add-seat --dir %USERPROFILE%/room-dev/rooms/demo --seat A --role reviewer --wait turn_over  --cwd <A 的空目录>   --audit codex  --wake-thread room-A
node <app>/room.mjs admin add-seat --dir %USERPROFILE%/room-dev/rooms/demo --seat B --role executor --wait background --cwd <任务项目目录> --audit claude

:: 2. 起服务（自己的终端，一直开着）
node <app>/room.mjs serve --dir %USERPROFILE%/room-dev/rooms/demo

:: 3. 对每个 agent 说一句话（路径写展开后的绝对路径）
::    「读 C:\Users\<你>\room-dev\rooms\demo\seats\A\JOIN.md，按它入席。」
::    「读 C:\Users\<你>\room-dev\rooms\demo\seats\B\JOIN.md，按它入席。」

:: 4. 给任务、开轮（另一个终端）
node <app>/room.mjs admin task  --dir %USERPROFILE%/room-dev/rooms/demo --text "……"
node <app>/room.mjs admin start --dir %USERPROFILE%/room-dev/rooms/demo --order A,B,A

:: 5. 看
node <app>/room.mjs admin show --dir %USERPROFILE%/room-dev/rooms/demo
node <app>/room.mjs admin log  --dir %USERPROFILE%/room-dev/rooms/demo
```

桌面应用 `圆桌.exe` 与圆桌启动器（2026-10-04）已经可以在窗口里建房建席、生成入席句子、打开房间界面；它们验证到什么程度见 `docs/SUPPORT-MATRIX.md`「桌面程序」一节。

## 9. 支持矩阵

见 [`docs/SUPPORT-MATRIX.md`](SUPPORT-MATRIX.md)。每格只取 已验证 / 未验证 / 不支持 三值，每个「已验证」都有脚注转述 P−1 探针报告里的那条发现。截至 2026-10-01，有已验证格子的只有两行：脚本席位（仿真端到端），和由探针会话用 `codex exec` 起、与房间同在一个包上下文的 Codex 线程。Codex Desktop 的交互线程、Codex CLI、Claude Code 这几行全部未验证（Claude Code 在探针里只有替身）。
